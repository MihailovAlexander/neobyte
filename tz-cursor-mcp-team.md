## 3. Архитектура: центральный MCP-хаб

### 3.1 Концепция

Все MCP-серверы разворачиваются на **одном выделенном сервере** (Ubuntu 24.04 LTS).  
Разработчики и аналитики подключаются к серверу из Cursor по **SSH** и/или обращаются к MCP по **HTTP** через локальный туннель или VPN.

```
┌─────────────────────────────────────────────────────────────────┐
│  MCP HUB SERVER  (Ubuntu 24.04, Docker)                         │
│                                                                 │
│  ┌──────────────────┐  ┌──────────────────┐  ┌───────────────┐  │
│  │  cfg_1_graph     │  │  cfg_1_code_meta │  │  cfg_1_help   │  │
│  │  (Neo4j + API)   │  │  (Chroma + API)  │  │  (RAG + API)  │  │
│  │  port 8036       │  │  port 8012       │  │  port 8003    │  │
│  └──────────────────┘  └──────────────────┘  └───────────────┘  │
│  ×15 конфигураций → свой стек портов (8036+N, 8012+N, 8003+N)   │
│                                                                 │
│  ┌─────────────┐  ┌──────────────┐  ┌────────────┐              │
│  │ ssl_mcp     │  │ templates    │  │ syntaxcheck│  ← shared    │
│  │ port 8008   │  │ port 8004    │  │ port 8002  │              │
│  └─────────────┘  └──────────────┘  └────────────┘              │
│  ┌──────────────────┐  ┌──────────────────────┐                 │
│  │ code_check_mcp   │  │ monitoring stack     │                 │
│  │ (1С:Напарник)    │  │ (Grafana+Prometheus  │                 │
│  │ port 8007        │  │  +Loki, port 3000)   │                 │
│  └──────────────────┘  └──────────────────────┘                 │
│                                                                 │
│  NVMe #1: ОС + Docker images + исходники (read-only mount)      │
│  NVMe #2: ТОЛЬКО индексы (Chroma DB, Neo4j data) ← отдельный    │
└─────────────────────────────────────────────────────────────────┘
         ▲ SSH (read-only shell для разработчиков)
         │ HTTP localhost tunnel / WireGuard VPN
┌────────┴────────────────────────────────────────────────────────┐
│  Рабочие станции: 10 разработчиков + 5 аналитиков               │
│  Cursor Desktop → .cursor/mcp.json → http://hub:PORT/mcp        │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 Структура портов (15 конфигураций × 3 сервера + shared)

| Конфигурация | graph_meta | code_meta | help_mcp |
|-------------|-----------|----------|---------|
| cfg_01 | 8036 | 8012 | 8103 |
| cfg_02 | 8037 | 8013 | 8104 |
| ... | ... | ... | ... |
| cfg_15 | 8050 | 8026 | 8117 |
| **Shared** | — | — | — |
| syntax_check | — | — | 8002 |
| templates | — | — | 8004 |
| ssl_mcp | — | — | 8008 |
| code_check | — | — | 8007 |

> HelpSearch: 6 версий платформы → 6 контейнеров на портах 8103–8108. Конфигурации делят между собой ближайшую версию платформы.

### 3.3 SSH-доступ для разработчиков

- **Read-only mount** папок с исходниками, rules, skills, MCP-конфигами через `--mount type=bind,readonly`.
- Разработчики видят структуру проекта через SSH (для Cursor Remote SSH extension), но **не могут изменять** файлы исходников и правил (chmod 550 / ACL).
- Права на запись только у выделенного `mcp-admin` пользователя и CI-скриптов пересчёта.
- Cursor Remote SSH: разработчик открывает папку `/opt/1c-projects/cfg_XX` → видит исходники → Cursor использует MCP с хаба автоматически через `.cursor/mcp.json` в папке проекта.

### 3.4 Тестовые базы 1С + OneMCP.cfe (отдельный сервер)

**OneMCP.cfe** — расширение 1С, которое публикует HTTP MCP-endpoint из **живой** ИБ (`…/hs/mcp`). Cursor через него может выполнять запросы к данным тестовой базы. Это **не** замена `code_meta` / `graph_meta` (индексы выгрузки) и **не** ставится на MCP Hub.

#### Почему не на AX102 / MCP Hub

На одном хосте с Docker-MCP поднимать **кластер 1С + СУБД** нецелесообразно: другой стек администрирования, лицензии платформы, бэкапы ИБ, обновления, конфликты ресурсов с ночным reindex. MCP Hub остаётся Linux + Docker; 1С — отдельная машина (Windows Server или Linux + ragent), уже привычная админам 1С.

#### Целевая схема

```
                    корпоративная сеть / WireGuard / VLAN
┌─────────────────────────────┐      ┌──────────────────────────────────┐
│  MCP Hub (Hetzner AX102)    │      │  1C Test Server (отдельный хост) │
│  code_meta / graph_meta     │◄────►│  Сервер 1С + СУБД                │
│  shared MCP, Grafana        │ HTTP │  15 тестовых ИБ                  │
│  Cursor Remote SSH          │      │  OneMCP.cfe в каждой ИБ          │
│                             │      │  Web (IIS/Apache) → /cfg_XX/hs/mcp│
└─────────────────────────────┘      └──────────────────────────────────┘
         ▲                                      ▲
         └──────── разработчик (VPN) ───────────┘
              mcp.json: hub localhost + URL OneMCP
```

| Компонент | Где | Назначение |
|-----------|-----|------------|
| `code_meta` / `graph_meta` | MCP Hub | Поиск по **выгрузке** CF (код, метаданные, impact) |
| OneMCP.cfe × 15 | **1C Test Server** | Вопросы к **данным** тестовой ИБ (запросы, справочники) |
| Боевые / прод ИБ | Не подключать | OneMCP только на тестовых копиях |

#### Сеть

- MCP Hub и 1C Test Server — **одна L2/L3 сеть** (VLAN, VPC, WireGuard site-to-site или частная сеть облака).
- Публикации `http://1c-test/cfg_XX/hs/mcp` **не в интернет**: ACL только с MCP Hub и/или VPN разработчиков.
- В `.cursor/mcp.json` на хабе для проекта `cfg_XX`: URL вида `http://1c-test.internal/cfg_XX/hs/mcp` (hostname 1C-сервера в частной сети). При Remote SSH вызов OneMCP идёт **с хаба** к 1C-серверу — оба в одной сети, без проброса наружу.

#### Состав 1C Test Server (ориентир)

- Платформа 1С (~6 версий — по возможности несколько ragent/кластеров или совместимые агенты под нужные релизы).
- 15 тестовых ИБ (клиент-сервер), в каждой установлено `OneMCP.cfe` + отдельная web-публикация только HTTP-сервиса MCP.
- Отдельный пользователь 1С на каждую ИБ (минимальные права; без интерактивного входа админа).
- СУБД: PostgreSQL или MS SQL — по стандарту компании; **не** на дисках MCP Hub.

#### Безопасность OneMCP

- Только тестовые базы (обезличенные / урезанные копии).
- Запрет публикации прод-ИБ.
- Rate limit / отдельный пул сеансов в `.vrd`.
- Логи вызовов MCP на стороне 1С + (по возможности) прокси/аудит на хабе.
- В правилах агента: OneMCP — только для запросов к данным теста; правки конфигурации через OneMCP не делать.

#### Смета

Аренда/железо **1C Test Server** — **отдельная строка OPEX**, не входит в AX102. Размер: от «один Windows Server 16–32 ГБ RAM» на пилот 3 баз до выделенного кластера под 15 ИБ (считать с админами 1С).

> Уточнение к старой формулировке: отдельные Docker-контейнеры `cfg_XX_test_graph` на хабе **не обязательны** для OneMCP. Тестовые индексы code/graph на хабе — только если нужна отдельная выгрузка «тест vs бой»; OneMCP к индексам не привязан.

## 4. Пересчёт индексов: I/O и расписание

### 4.1 Реальная нагрузка на диск при пересчёте

При индексации одной конфигурации (~1 ГБ выгрузки):

| Операция | Тип нагрузки | Объём | Время (HDD→NVMe) |
|---------|--------------|-------|-----------------|
| Чтение CF-выгрузки | Sequential read | ~1 ГБ | 10–30 сек (NVMe) |
| Построение Chroma (code_meta) | Random write | ~2–4 ГБ в индексе | 30–90 мин |
| Построение Neo4j (graph_meta) | Random read+write | ~3–6 ГБ | 60–180 мин |
| Итого на 15 конфигураций | — | ~75–150 ГБ индексов | ~8–20 ч (sequential) |

**Вывод:** полный пересчёт 15 баз — это 8–20 часов. При выделенном NVMe под индексы и параллельном пересчёте (4 базы одновременно) — 3–6 часов. Это укладывается в ночное окно (00:00–06:00).

### 4.2 Почему отдельный NVMe критичен

- Индексация создаёт **random I/O до 100K IOPS** на Chroma и Neo4j.
- На общем диске это вытесняет кэш ОС, тормозит Docker и SSH.
- На отдельном NVMe (1–2 ТБ, PCIe 4.0) индексация изолирована — рабочие процессы не замечают.

### 4.3 Расписание пересчёта

```
Ночь (00:00 – 05:00):
  - Скрипт проверяет Хранилище 1С — есть ли изменения с последнего пересчёта
  - Если есть → выгрузка в файлы (автоматически) → пересчёт code_meta + graph_meta
  - Параллельно: до 4 конфигураций одновременно

Выходные (Сб 22:00 – Вс 06:00):
  - Полный пересчёт всех 15 конфигураций (принудительный)
  - Обновление HelpSearch MCP (если вышла новая версия платформы)

По требованию (ручной запуск):
  - Команда в Mattermost: @mcp-bot reindex cfg_05
  - Запускает пересчёт одной конфигурации немедленно
```

### 4.4 SLA-мониторинг

- Каждый MCP-стек пишет метку `last_indexed_at` в Redis/файл.
- Prometheus-метрика `mcp_index_age_hours{cfg="cfg_01"}`.
- Alertmanager: если `index_age > 168 ч (7 дней)` → уведомление в Mattermost `#mcp-alerts`.
- Grafana-дашборд: статус всех 15 конфигураций, время последнего пересчёта, тренд.

## 5. Мониторинг MCP

### 5.1 Стек мониторинга (всё self-hosted на том же сервере)

```
Prometheus  → собирает метрики с MCP-контейнеров + node_exporter
Loki        → сбор логов всех Docker-контейнеров (docker log driver)
Grafana     → единый дашборд (доступен по HTTP, порт 3000)
Alertmanager → роутинг алертов в Mattermost (webhook)
```

### 5.2 Что отслеживается

| Метрика | Порог алерта | Канал |
|---------|-------------|-------|
| MCP-контейнер упал (HTTP 5xx / no response) | немедленно | `#mcp-alerts` |
| Индекс отстал > 7 дней | немедленно | `#mcp-alerts` |
| Индексация завершена успешно | — | `#mcp-status` (info) |
| Индексация завершилась с ошибкой | немедленно | `#mcp-alerts` |
| RAM > 85% | 15 мин | `#mcp-alerts` |
| Диск индексов > 85% | немедленно | `#mcp-alerts` |
| Время ответа MCP > 10 сек | 5 мин | `#mcp-alerts` |

### 5.3 Алерты в Mattermost

Все уведомления идут в Mattermost через Incoming Webhook:
- `#mcp-alerts` — ошибки, деградации, SLA-нарушения
- `#mcp-status` — успешные пересчёты, плановые операции
- Формат: `[ALERT] cfg_05 graph_meta: index_age = 8 days. Last indexed: 2026-08-16 02:10`

Команды админа (slash / бот): `@mcp-bot reindex cfg_05`, `@mcp-bot status`.

### 5.4 Лицензия Mattermost — хватит ли бесплатной

**Да, для этого проекта хватит Mattermost Team Edition (MIT, $0).** Конечные пользователи (50 чел.) в Mattermost не заводятся — им Open WebUI. В Mattermost только IT: ~15 человек + боты.

| Издание | Цена | Лимит пользователей | Что важно для нас |
|---------|------|---------------------|-------------------|
| **Team Edition (рекомендуем)** | $0, MIT, self-hosted | Ориентир до **250** activated users | Каналы, webhook, slash-команды, боты, **без лимита истории сообщений**. SSO (LDAP/SAML) **нет** — логин/пароль или локальные аккаунты. |
| Entry (бесплатная коммерческая) | $0, но EULA | Рекомендуют < 50 | SSO есть, но **история чата ~10 000 сообщений** — плохо для логов алертов. Не брать. |
| Professional / Enterprise | платно | без жёсткого потолка | LDAP/SAML, HA, compliance. Нужно только если появится корпоративный SSO в Mattermost. |

Нужные функции (incoming webhook, каналы `#mcp-alerts` / `#mcp-status`, бот reindex) входят в Team Edition.

Не путать с Entry: выглядят «бесплатно и с фичами», но режут историю — для мониторинга это хуже.

**Если Mattermost по оргпричинам не ставят:** те же алерты уходят в Grafana OnCall / email. Каналы и slash-команды тогда теряются.

## 6. Варианты embedding: OpenRouter vs. локальный GPU

Embedding-модели нужны для **семантического поиска** в code_meta и graph_meta (Chroma). Качество семантического поиска напрямую зависит от модели.

### Вариант A: OpenRouter API (внешний)

| Параметр | Значение |
|----------|---------|
| Модель | `text-embedding-3-large` (OpenAI via OpenRouter) или `voyage-code-2` |
| Качество | Высокое (sota для кода) |
| Задержка пересчёта | Зависит от API rate limit (~2–4× медленнее GPU) |
| Стоимость embedding при пересчёте 15 баз | ~$15–40 за полный пересчёт (15 ГБ × $0.13/млн токенов) |
| OPEX в месяц (еженедельный полный пересчёт) | ~$60–160/мес |
| Плюсы | Не надо GPU; легко масштабировать; нет инфраструктуры |
| Минусы | Зависимость от интернета; GDPR/ПДн (код уходит наружу); rate limits |

### Вариант B: Локальный GPU (без OpenRouter)

| Параметр | Значение |
|----------|---------|
| Рекомендуемая модель embedding | `Qwen3-Embedding` (8B) или `BAAI/bge-m3` |
| GPU | NVIDIA RTX 4090 (24 GB VRAM) или A10G |
| LM Studio / Ollama | Для сервинга embedding-модели локально |
| Качество | Сопоставимо с text-embedding-3-large на коде BSL |
| Время пересчёта 15 баз | ~3–5 ч (параллельно, GPU) |
| Стоимость GPU (аренда облако) | $0.75–1.20/ч → ~$100–200/мес при ночных пересчётах |
| Или купить RTX 4090 | ~$1,800 CAPEX (окупается за ~10–12 мес) |
| Плюсы | Код не уходит наружу; нет лимитов; ниже OPEX после окупаемости |
| Минусы | CAPEX или аренда GPU; администрирование LM Studio |

### Рекомендация

**Старт (пилот, 1–3 мес): Вариант A (OpenRouter)** — быстрее запуститься, нет CAPEX на GPU. Ограничение: не отправлять в API приватные данные клиентов (только код BSL/метаданные — допустимо).

**Продакшн (после пилота): Вариант B (локальный GPU)** — ниже риски ИБ, ниже OPEX, нет зависимости от внешнего API. Рекомендуется арендовать GPU-сервер (облако), а не покупать железо до подтверждения ROI.

**Для LLM (генерация ответов в Cursor)** — оба варианта используют Cursor Pro (модели Claude/GPT через Cursor): это отдельно от embedding.

## 8. Безопасность

### 8.1 Доступ разработчиков к серверу

- SSH-ключи (no password auth), отдельный пользователь `dev-readonly` без sudo.
- Исходники конфигураций: `/opt/1c-projects/cfg_XX/` → `chmod -R 550`, owner `mcp-admin`.
- Cursor Remote SSH: разработчик подключается как `dev-readonly`, видит исходники, но не может изменить.
- MCP-правила (skills, rules, agents): `/opt/cursor-rules/` → `chmod -R 550`, read-only bind mount в каждый проект.
- `mcp-admin` (sudo) — только у администратора MCP.

### 8.2 Сетевая изоляция

- MCP-порты (8000–8200) не открываются наружу — только через SSH-туннель или WireGuard VPN.
- Grafana (3000) — только по VPN.
- Outbound: OpenRouter (вариант A) — whitelist по IP; Git-хранилище — по SSH-ключу.

### 8.3 Секреты в правилах и агентах

Вопрос 33 касался следующего: правила и агенты (`.cursor/rules/`, `AGENTS.md`) могут содержать токены, пароли ИБ, API-ключи если разработчик случайно их туда сохранит.

**Политика:**
- Все секреты хранятся только в `.dev.env` (gitignored).
- В rules/agents/skills — только плейсхолдеры (`{{INFOBASE_PASSWORD}}`).
- Pre-commit hook на сервере: grep на паттерны `password`, `token`, `api_key`, `license` в `.cursor/rules/` — блокирует коммит.
- Регулярный аудит: `grep -r "KEY\|TOKEN\|PASS" /opt/cursor-rules/` по cron (ежесуточно), алерт в `#mcp-alerts`.

### 8.4 Безопасность web-чата (фаза 2)

- Запрет на выполнение кода (sandbox BSL-интерпретатор отключён).
- Запрет на выгрузку данных из ИБ (MCP не подключён к живой ИБ, только к индексу).
- Rate limiting: не более 20 запросов/мин на пользователя.
- Аудит-лог всех вопросов и ответов (в Loki + Grafana).
- Маскирование ПДн: фильтр по регулярным выражениям перед отправкой в LLM (ФИО, ИНН, СНИЛС, телефон).
- Модерация контента: список запрещённых тем (финансовые данные клиентов, коды доступа, SQL-запросы к ИБ).
- JWT-аутентификация (корпоративный SSO или отдельная база пользователей).

## 9. Web-чат для конечных пользователей (фаза 2)

### 9.1 Рекомендуемая архитектура

```
Пользователь → Web UI → Chat API → System Prompt + MCP Context → LLM
                                              ↓
                                   MCP Hub (code_meta / graph_meta)
                                   Выбор конфигурации из списка
                                              ↓
                                   Audit Log → Loki → Grafana
```

**Рекомендация:** Развернуть **Open WebUI** (open-source, MIT) — это готовый web-интерфейс чата с поддержкой:
- Списка «ботов» / системных промптов → каждый бот = конфигурация 1С.
- Pipe-функций (plugin API) → можно вызывать MCP-инструменты прямо из чата.
- Аудит-лога всех диалогов.
- Графика использования (встроенный дашборд).
- RAG-коллекций (загрузка PDF-документации).
- LDAP/OAuth2 для SSO.

### 9.2 Flow для пользователя

```
1. Вход (SSO или логин/пароль)
2. Выбор конфигурации из списка (cfg_01 "Бухгалтерия", cfg_02 "ЗУП", …)
3. Выбор контекста: "Как пользователь", "Как аналитик" (разные system prompt)
4. Чат → вопросы на русском
5. Ответ: текст + ссылки на объекты метаданных + описание процесса
```

### 9.3 Варианты интеграции

| Вариант | Плюсы | Минусы | Рекомендация |
|---------|-------|--------|-------------|
| **Open WebUI** (self-hosted) | Полный контроль, бесплатно, аудит, pipe-MCP | Надо поддерживать | ✅ Рекомендуется |
| Mattermost (бот) | Team Edition бесплатна; webhook + slash | Не UI для 50 пользователей; SSO нет | ✅ Как дополнение для IT (алерты + reindex) |
| Telegram-бот | Привычен пользователям | Данные уходят в Telegram, GDPR, нет аудита в контуре | ⚠️ Только если нет других вариантов |
| Встроить в 1С (Web-клиент) | Максимально привычно | Сложная интеграция, нет готовых компонент | ❌ Сложно, фаза 3+ |

**Итог:** Open WebUI как основной интерфейс + Mattermost-бот для команды IT (мониторинг, ручной reindex, алерты).

### 10.2 Лицензии Cursor: Pro vs Teams/Business

| Тип | Цена | Что даёт |
|-----|------|----------|
| **Cursor Pro** (выбрано) | $20/мес/чел | AI в IDE как у Business по сути; оплата через ЗП/компенсацию |
| Cursor Teams / Business | $40/мес/чел | То же + единый счёт, admin dashboard, SSO, enforced privacy mode, аналитика usage |

**Для 15 человек → Cursor Pro, $300/мес** (+$20 к компенсации каждому).

#### Доступ к MCP при увольнении

MCP и исходники живут на хабе. Доступ — только через **корпоративный VPN + SSH**. При увольнении: снять VPN + отозвать SSH-ключ → доступ к MCP и CF сразу пропадает. Это **не** функция Cursor Business.

Pro-подписка у уволенного может остаться личной — без VPN/SSH он не видит ваши базы. Чеклист offboarding: VPN off → SSH revoke → прекратить компенсацию Pro → (по возможности) попросить удалить локальные кэши Cursor.

#### Нужен ли Business / Teams?

При схеме «хаб + VPN» **для отзыва MCP — нет**. Pro достаточно.

Business/Teams имеет смысл только если заказчику отдельно нужны:

| Фича Teams | Есть ли у вас замена | Когда платить ×2 |
|------------|----------------------|------------------|
| Мгновенно снять seat Cursor | Нет (только отменить компенсацию / аккаунт вручную) | Если критичен «день в день» revoke IDE, не только VPN |
| Enforced privacy mode (код не уходит в training) | У Pro privacy включается вручную, сотрудник может выключить | Если ИБ требует **принудительно** org-wide |
| Один счёт / admin dashboard / usage по людям | Нет (15 отдельных Pro) | Если бухгалтерии/владельцу продукта нужен единый контроль расходов |
| SSO (SAML/OIDC) | Нет | Если корпоративный IdP обязателен |
| Shared team rules / marketplace | Rules лежат на хабе в `/opt/cursor-rules` (read-only) | Обычно не нужно |

**Рекомендация ТЗ:** старт на **Pro**. Переход на Teams — только если после пилота ИБ/финансы потребуют SSO, enforced privacy или единый биллинг. Доступ к MCP при этом по-прежнему закрывается VPN/SSH, не тарифом Cursor.

## 12. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Полный пересчёт > 8 ч (не успевает за ночь) | Средняя | Среднее | Параллелизм × 4, GPU (вариант B) |
| OpenRouter rate limit при пересчёте | Средняя | Среднее | Retry-логика, уменьшить batch size |
| NVMe заполнен > 85% | Низкая | Высокое | Алерт Prometheus, 2 ТБ с запасом |
| Разработчик случайно сломает read-only mount | Низкая | Среднее | chmod 550, audit log изменений |
